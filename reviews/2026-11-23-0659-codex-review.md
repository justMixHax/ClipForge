The publishing implementation cannot complete a new YouTube resumable upload against the real API, and manual timestamp adjustment can create invalid clip intervals. Date-filtered post history is also incomplete.

Full review comments:

- [P1] Include Content-Range on the initial YouTube upload
  **Fixed: every piece of a YouTube upload now carries Content-Range, the first one too, and the stand-in
  YouTube used by the tests refuses an upload without it, so this cannot hide again.** — backend/app/publishing/youtube.py:220-221
  For a new resumable YouTube upload `offset` is zero, so this branch omits `Content-Range` entirely. YouTube's resumable upload protocol requires that header for each media PUT, including `bytes 0-(size-1)/size`; the local fake defaults a missing range to zero and therefore masks this, but real initial YouTube uploads will be rejected.

- [P2] Keep adjusted manual timestamps within a valid interval
  **Fixed: the end is settled first; the start moves to a word's edge only if at least a second of clip
  remains. Two tests: the shortest selection, and a start next to the end of the video.** — backend/app/analysis/engine.py:459-462
  When a user-selected start falls near the end of a word, this moves it forward without checking the supplied/end-derived boundary. For example, a one-second explicit selection whose start is moved 0.6 seconds can be saved as a sub-second clip; near the video's final word, the adjusted start can exceed the clamped video-duration end entirely. The resulting `Clip` has `end <= start`, causing the subsequently queued render to fail or produce invalid output.

- [P2] Apply the end filter to publication times
  **Fixed: a date range now selects posts by when they go or went live (scheduled, else published, else
  queued), the same moment the calendar uses. One test.** — backend/app/api/publishing.py:158-159
  When callers provide an `end` bound, posts published within that bound but created and scheduled before it are omitted because this predicate does not include `Post.published_at`. This is asymmetric with the `start` filter and makes date-range queries return an incomplete publishing history, especially for immediately posted clips.
